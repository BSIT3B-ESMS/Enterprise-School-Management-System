# Payroll Management System (PMS)

This original-workflow migration build replaces the browser-state prototype with a Laravel server application. Accounts, schedules, requests, attendance, payroll results, releases and audit events persist in MySQL. The browser does not store the authoritative roster or calculate pay.

Read UPGRADE-FROM-V7.md before upgrading an existing database. Preserve its APP_KEY.

## Original TAP user interface restored (Laravel 13 integration build)

This build keeps the original v4 **navy/brass TAP visual language**, animated-dial sign-in, top masthead, horizontal module ribbon and pagebar, now generated by Laravel Blade. The content is backed by the Laravel database. The kiosk scan and the original five-tab navigation and leave/appraisals flows were restored. Some screen layouts remain adapted to forms and payroll records supported by the v6 server; it is **not** the old static v4 HTML or browser-simulated payroll.

- Sign in: `/login` (Employee ID / Admin ID and password, session CSRF, admin TOTP). First installation: `/setup`.
- Administrator dashboard: `/`; employee landing screen: `/?page=attendance`; original five-tab navigation is restored. Admin secondary tools (reports, kiosk management, settings, audit) remain at `/?page=...` links from dashboard/payroll.
- `public/tap-pms-ui/css/style.css` and `tap-theme.css` come from the original v4 archive; `bridge.css` adapts the v6 server UI. None of the old `app.js`/`store.js` localStorage-auth screens are used.
- The old `/tap-pms-ui/index.html` page is deliberately absent: it had mock account credentials and client-side payroll which could be mistaken for authentic records.
- For local development **without live EMS**, the administrator can import an **official EMS-exported roster** in Settings. Required header: `employee_no,full_name,department,position,monthly_rate,status,salary_effective_on,updated_at`. Do not invent or replace EMS IDs. The upload is strictly disabled in production and when EMS integration is on. No seed users or sample employee files are shipped.
- Real EMS integration requires the other team's approved endpoint paths, tokens and response-field mappings, per `docs/EMS-CONNECTION.md` and `docs/API-STANDARD.md`. Its live success cannot be guaranteed without their server.

**Windows upgrade note:** Extract alongside the previous build, not over your live folder. Copy your existing `.env` (and backup your MySQL `tap_pms` database and private `storage` evidence separately), run `composer install`, `php artisan config:clear`, `php artisan migrate`, then `php artisan serve`. When using XAMPP with PHP 8.2 and separate PHP 8.4 in Downloads, ensure `php -v` and `composer -V` both reference PHP 8.4 in the active terminal. Open `http://127.0.0.1:8000/login`, not `/tap-pms-ui/index.html`.

**Validation:** this aligned build passed **66 tests / 357 assertions** using PHP 8.4, Laravel 13, Pest and MySQL 8. Browser acceptance also passed for original navigation, setup/MFA, PMS-owned schedule assignment, employee-ID login, payroll/release/PDF, reports, leave filing, official balance display and responsive profile layout. See TESTING.md for limits.

**Ownership confirmed:** PMS manages employee work schedules. EMS supplies employee records, effective salaries, leave decisions and remaining leave balances. No EMS schedule feed is required. See `docs/OWNERSHIP.md`.

**Integration handoff:** the PMS adapter follows the shared standard, but the inspected EMS source still needs its leave/balance API endpoints and employee cursor/money/effective-date updates. `docs/EMS-TEAM-REQUIREMENTS.md` documents the exact remaining work. Included round-trip tests simulate that agreed contract; they do not certify live connectivity.

## Required stack

PHP 8.4.x; Laravel 13; MySQL 8; Composer 2; Blade, Bootstrap 5.3, jQuery and jQuery UI; Pest 4. Frontend assets are bundled locally. No Node build or internet CDN is required to run the portal. Composer installs the locked PHP dependencies, including the PDF renderer.

Enable PHP extensions required by Composer, especially PDO MySQL, mbstring, openssl, fileinfo, DOM/XML and GD. An existing XAMPP installation with an older PHP version must use PHP 8.4 for this project. Check `php -v` and `composer check-platform-reqs`.

## First run on Windows

1. Extract this ZIP. Open a terminal in the folder containing `artisan` and `composer.json`.
2. Start MySQL 8. Create an empty `tap_pms` database with utf8mb4 and a dedicated database user allowed to create/alter tables in that database. Do not use the test database for real records.
3. Run:

```bat
copy .env.example .env
composer install
php artisan key:generate
```

4. Edit `.env`: set `DB_HOST`, `DB_PORT`, `DB_DATABASE`, `DB_USERNAME`, `DB_PASSWORD` for your MySQL installation. Keep the generated `APP_KEY` private and retain it in backups; it encrypts MFA secrets.
5. Run:

```bat
php artisan migrate
php artisan serve --host=127.0.0.1 --port=8000
```

6. Open http://127.0.0.1:8000/setup. Create the first administrator and enroll an authenticator using the displayed secret. Save the recovery codes privately. There are no default administrator credentials. The setup page closes after the first administrator exists.

For later local runs, start MySQL and double-click `start-tap-pms.bat`, or use the serve command above. Do not open a standalone HTML file. On macOS/Linux, use `cp .env.example .env` in place of `copy`.

## Prepare the system

1. Import EMS employee records with their official employee numbers and effective salary dates. Use the configured EMS synchronization or the operator JSON import in `docs/EMS-CONNECTION.md`.
2. Under Settings, confirm the institution's monthly divisor, overtime multiplier, holiday dates and report signatory. These are required inputs, not assumed official policy.
3. Under Workforce, assign each employee an effective work schedule and workdays, card UID and login account. Share the initial password privately; employees can change their own password. EMS owns names, employment status and salary; PMS does not issue real employee numbers.
4. Authorize a kiosk **once in the same browser** by opening `/kiosk` while signed in as Admin (MFA verified), choosing Activate this browser; the application signs the administrator out automatically to leave a safe employee-facing scanner. A token-based alternative is available behind optional details for a remote kiosk. Revoke device authorization in Settings if lost. Employees never choose their own AM/PM event; the server resolves it from the effective schedule and saved punches.
5. Record attendance or approve documented attendance corrections. Employees can file overtime, schedule changes, corrections, loan/tax/deduction and leave requests with private proof attachments.
6. Approve or reject PMS-owned requests. Leave approval stays with EMS: submit the leave request to EMS, then synchronize the EMS decision. Filing a leave request alone does not make it paid or approved.
7. Select the payroll cut-off and compute. Review attendance, pending requests and each calculation before releasing individual employee payslips. Only released payslips are visible to employees. Withdraw releases before correcting/recomputing a cut-off that contains released payslips.
8. Generate payroll, attendance or request reports. Each stored report has a control number, signatory and CSV/PDF downloads. Payslips also download as real PDFs.

For an empty local sandbox only, `php artisan pms:demo-data --confirm` creates one clearly synthetic employee, schedule and random employee password shown once. It does not create an administrator or real EMS data. Normal migrations and seeders create no demo accounts.

## Attendance and payroll behavior

- Automatic four punches: AM IN, AM OUT, PM IN, PM OUT. Employees scan a card and take a live photo; there is no manual event dropdown. Time comes from the server in UTC; attendance work dates and schedules use Asia/Manila. Lunch is excluded from scheduled working minutes.
- PM-only work remains PM-only; the app does not fabricate an AM punch. Unworked scheduled minutes produce an attendance deduction. A completely absent session is deducted without creating a punch. An unmatched IN/OUT blocks release until reviewed/corrected.
- Monthly basic pay is divided into two cut-offs. Effective salary changes within a cut-off are weighted by scheduled workdays. The configured monthly divisor is used for daily/minute deduction and overtime rates.
- Only approved overtime and approved/administrator-entered adjustments affect pay. Amounts use integer centavo arithmetic; outgoing money is a two-decimal string.
- Paid, full-day EMS-approved leave covers that day's schedule; unpaid leave is not double deducted. Conflicting leave and punches require review.
- Automatic official employee deductions are restored: dated SSS / GSIS coverage, PhilHealth, Pag-IBIG and BIR semi-monthly withholding. Confirm each employee’s coverage in Workforce before computation; SSS and GSIS are alternatives. Effective-dated overrides support confirmed exceptions and recurring loan amounts. See docs/STATUTORY-RULES.md. Holiday premiums, overnight shifts and mixed/partial-day leave still require an agreed institution policy.
- Inactive, retired, terminated and resigned employees are blocked from new login/punch/payroll eligibility; historical records remain. Released calculations are retained as snapshots. Changed inputs must be recomputed before a fresh release.
- With EMS enabled, release requires successful employee and leave synchronization within the last 24 hours. With EMS disabled, operator-import mode is available for local evaluation; it cannot establish that remote EMS data is current.

## Phone / LAN kiosk

Local desktop: use `127.0.0.1`. For a LAN evaluation, run `php artisan serve --host=0.0.0.0 --port=8000`, allow that port on the private network, and access the host computer's LAN address from the phone. This development server is for evaluation.

The kiosk requires a live photo on each scan. A USB reader acts as a keyboard, while supported Android browsers can use Web NFC. Camera and Web NFC require a browser-trusted secure context. A plain HTTP LAN IP generally does not provide that. Use an institution-managed HTTPS endpoint with its web root set to `public`, and set `APP_URL` accordingly. Set `SESSION_SECURE_COOKIE=true` when HTTPS is in use; leave it false for localhost HTTP. Web NFC also depends on supported Android hardware/browser and card technology. A USB reader can type a card UID; camera/file capture is offered as a fallback. Hardware and real-device acceptance still require testing on your own kiosk.

## Application API

See `docs/API-STANDARD.md` (supplied standard, unchanged) and `docs/openapi.json` (implemented contract).

```bat
php artisan pms:token accounting --permission=payslips:read --permission=payroll-periods:read
php artisan pms:token accounting --revoke
```

The token prints once; keep it on the calling application's server. Never put it in browser JavaScript. `/api/v1` uses named permissions, Bearer tokens, cursor paging, UTC timestamps and two-decimal money strings. POST requests require a UUID `Idempotency-Key`; matching retries replay the stored response for at least 24 hours and changed bodies return 409. The limit is 60 requests per minute per token. Read permission includes drafts, so issue it only to integrations authorized to see them; consumers can request `status=released`.

POST `/payslips` accepts only the period and employee identifiers as business inputs. Payroll amounts are calculated by PMS; supplied monetary totals are rejected. Release is an authenticated administrator workflow. PMS owns UUID period/payslip IDs; EMS owns employee numbers. Cross-team display conventions and real EMS paths must be agreed with the other team.

## Tests

Create a separate `tap_pms_testing` database and grant the test user rights only to it. Copy `.env.testing.example` to `.env.testing`, set the test connection, then run `php artisan test`. Tests rebuild tables in that test database. Never point them at production. See `TESTING.md` for the delivered validation record.

## Deployment / backup

Use `APP_ENV=production`, `APP_DEBUG=false`, HTTPS and a dedicated MySQL account. Set the web root to `public`; do not expose the project root or private storage. Back up MySQL, private evidence and `APP_KEY` together and test restoration. No `storage:link` is needed for private evidence; authorized controller routes serve it. The ZIP omits credentials, test databases, vendor dependencies and private uploads. Install dependencies through Composer.

Migration from an older prototype is not automatic: back up its data, map employee identifiers to EMS, validate attendance and reconcile a trial payroll before importing real records. The former browser snapshot is not an authoritative payroll database.

## Important current EMS contract limitation (verified against EMS source 2026-10-30)

See `docs/EMS-ACTUAL-CONTRACT-GAPS.md`. The publicly visible EMS API currently paginates employees using offset pages, returns a floating-point `base_rate` with no confirmed payroll units/effective-date history, and exposes no corresponding leave or balance API routes. These are blockers for a truthful live EMS payroll integration. Do not enable EMS or release real payroll until the EMS team supplies signed contracts that satisfy the `API.md` standard.

## Upgrading from the previous integrated login build

Apply `TAP-PMS-Original-Workflow-PATCH.zip` into the installed project root only after backing up MySQL and `storage` (the patch intentionally does not contain `.env`, `vendor`, or personal data). No `composer install` is necessary when the existing `vendor/autoload.php` already exists and dependencies did not change. **One additive migration** tracks EMS-suspended accounts: `php artisan migrate`. Do not use `migrate:fresh`, `db:wipe`, or regenerate `APP_KEY`. Then run `php artisan optimize:clear` and restart `php artisan serve`.

The tested areas are explicitly listed in `docs/ORIGINAL-WORKFLOW-VALIDATION.md`. Do not claim full original screen parity until the UI/browser tests and real EMS connection pass.
